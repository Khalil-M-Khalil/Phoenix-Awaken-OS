# Phoenix Awaken OS v0.1 Specification

## Product Goal

Phoenix Awaken OS is a desktop operating system concept for privacy-conscious work, local evidence handling, and explainable GRC decisions. Version 0.1 does not attempt to be a complete secure distribution. It validates the Evidence Capsule workflow that will later become a first-class desktop service.

## Primary User Story

A user boots or installs Phoenix Awaken OS, creates a case, selects a local artifact, records its trust context, calculates a streaming SHA-256 fingerprint, maps the artifact to a risk or control, records a decision, and exports a verifiable handover package without uploading the artifact.

## Functional Requirements

| ID | Requirement | v0.1 |

| FR-01 | Create a uniquely identified capsule. | Required |
| FR-02 | Store title, trust level, timestamps, and optional risk/control mapping. | Required |
| FR-03 | Hash large files incrementally without reading them into memory in full. | Required |
| FR-04 | Record evidence metadata and a timeline. | Required |
| FR-05 | Record operator decisions explicitly. | Required |

| FR-10 | Encrypted persistent capsule store. | Future milestone |

## Threat Model Summary

The first prototype assumes that the operator may handle an untrusted file, may accidentally choose the wrong evidence path, and may need to prove whether a file changed during handling. It therefore prioritizes explicit paths, incremental hashing, timestamps, trust labels, and operator decisions.

The prototype does not assume that the host operating system is uncompromised, that a SHA-256 hash proves the file is safe, or that a Markdown report is a legal or forensic certification. It does not provide anonymity, exploit prevention, malware eradication, or automatic deletion.

## Non-Goals

Version 0.1 does not include offensive security tools by default, hidden telemetry, cloud upload, password collection, IP blocking, self-deletion, irreversible host modifications, or unattended evidence classification.

## Acceptance Criteria

The milestone is accepted when the test suite passes, a synthetic file can be hashed and exported locally, invalid trust values are rejected, missing evidence is rejected, and the repository contains enough documentation for another developer to reproduce the result. The next milestone begins only after the model is reviewed and its persistence and cryptographic design are agreed.


## Fedora Atomic Image Path

The planned image path is based on Fedora's bootc model: a bootable OCI container image contains the kernel and userspace needed to boot as a host system, while the target system can receive upgrades through container-image delivery. The bootc project describes this as applying container layers to bootable host systems rather than running the host userspace as an ordinary application container.[1]

The current sandbox does not provide `podman`, `buildah`, `bootc`, or QEMU, so no image build is claimed yet. The next implementation step is to create a reproducible Containerfile and build instructions, then run them in an environment that provides the required container and virtualization tools.

## Base Image Verification Note

Fedora's official Atomic Desktop page identifies **Kinoite** as the atomic KDE Plasma desktop. The attempted pull of `quay.io/fedora-atomic-desktops/kinoite:44` was rejected by the registry, while the Fedora `fedora-bootc` repository is available as a public bootc base. Therefore, the first reproducible build should either use a verified public Kinoite image reference discovered from Fedora's current release metadata or use `quay.io/fedora/fedora-bootc:44` with a deliberately smaller, tested desktop layer. We will not treat an unverified image path as final.

The original full KDE package installation downloaded more than 650 RPMs and stopped on a slow mirror while fetching `qt6-qtpdf`; this is a network/mirror failure, not yet evidence that the architecture is invalid. The next build attempt should use a verified base image and, where possible, a stable mirror or cached package layer.
